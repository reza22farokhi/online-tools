امنیت JWT: بهترین روش‌ها و جلوگیری از آسیب‌پذیری

📅 ۱ آذر ۱۴۰۵ ⏱️ ۶ دقیقه مطالعه

اگر با ساختار و مفاهیم پایه JWT آشنا نیستید، ابتدا مقاله JWT چیست؟ را مطالعه کنید.

در دهه اخیر، **JWT (JSON Web Token)** به استاندارد طلایی احراز هویت در وب تبدیل شده است. از APIهای ابری گرفته تا سیستم‌های ورود تک‌مرحله‌ای، همه از JWT استفاده می‌کنند. اما این محبوبیت باعث شده بسیاری از توسعه‌دهندگان، مفاهیم امنیتی آن را نادیده بگیرند.

JWT چیست و از چه بخش‌هایی تشکیل شده؟

یک توکن JWT از سه بخش تشکیل شده که با نقطه (`.`) از هم جدا می‌شوند:

  • Header (سرآیند): الگوریتم امضا (مثل HS256) و نوع توکن (JWT).
  • Payload (داده‌ها): اطلاعات کاربر مثل User ID، نقش‌ها و تاریخ انقضا (exp).
  • Signature (امضا): هش رمزنگاری شده که اصالت توکن را تضمین می‌کند.

تفاوت حیاتی: رمزگشایی (Decode) ≠ تایید (Verify)

بزرگترین اشتباه امنیتی، تصور این است که JWT یک توکن مخفی است. این کاملاً غلط است! هر کسی با یک ابزار ساده می‌تواند Header و Payload را رمزگشایی کند، چون آن‌ها فقط به Base64URL کدگذاری شده‌اند (نه رمزنگاری!).

شما می‌توانید با ابزار رمزگشای JWT ما، محتوای هر توکنی را ببینید. اما در نظر داشته باشید که این فقط خواندن است، نه تایید اصالت. تایید واقعی باید در سرور با استفاده از کلید مخفی (Secret) انجام شود.

«JWT هرگز برای مخفی کردن داده طراحی نشده است. امنیت آن به امضای دیجیتال بستگی دارد، نه به مخفی بودن محتوا.»

۵ اشتباه امنیتی مرگبار در استفاده از JWT

  1. ذخیره اطلاعات حساس در Payload: شماره کارت بانکی، رمز عبور یا اطلاعات پزشکی هرگز نباید در JWT باشند.
  2. نادیده گرفتن تاریخ انقضا (exp): توکن باید بعد از مدت کوتاه (مثلاً ۱۵ دقیقه) منقضی شود.
  3. استفاده از الگوریتم "none": بعضی کتابخانه‌ها به اشتباه اجازه می‌دهند توکن بدون امضا پذیرفته شود (حمله None Algorithm).
  4. کلید مخفی ضعیف: Secret باید حداقل ۲۵۶ بیت آنتروپی داشته باشد. از ابزار تولید هش SHA-256 یا UUID برای تولید تصادفی استفاده کنید.
  5. ذخیره JWT در LocalStorage: به دلیل خطر حمله XSS، بهتر است توکن را در HttpOnly Cookie ذخیره کنید.

چگونه JWT را در مرورگر امن بررسی کنیم؟

برای دیباگ یا بررسی سریع توکن‌ها در طول توسعه، ابزار JWT Decoder ما گزینه ایده‌آلی است، چون:

  • توکن به هیچ سروری ارسال نمی‌شود (۱۰۰٪ Client-Side).
  • تاریخ انقضا را با کد رنگی نمایش می‌دهد.
  • Timestamp را به زمان خوانا تبدیل می‌کند.

اما به یاد داشته باشید: هرگز توکن‌های Production حساس را در هیچ ابزار آنلاین (حتی امن) وارد نکنید.

جمع‌بندی

JWT یک ابزار قدرتمند است، اما امنیت آن به درک درست شما بستگی دارد. تفاوت بین رمزگشایی و تایید، طول عمر کوتاه توکن‌ها، و ذخیره‌سازی امن کلید مخفی، سه ستون اصلی امنیت JWT هستند.

JSON Web Tokens (JWTs) are often used to carry claims between an identity provider, an application, and an API. They are useful, but a common implementation mistake is to treat a decoded token as a trusted identity. A JWT is only trustworthy after the receiving system validates it correctly.

JWT structure

A compact signed JWT commonly contains three Base64URL-encoded segments separated by periods:

  • Header: identifies the token type and the signing algorithm.
  • Payload: contains claims such as a subject, issuer, audience, and expiration time.
  • Signature: allows a verifier with the appropriate key to detect unauthorized changes.

Decoding is not verification

Base64URL is an encoding, not encryption. Anyone who obtains a typical signed JWT can read its header and payload. Decoding only displays those values; it does not prove who issued the token or whether the claims are valid. The signature must be verified using a trusted key and a maintained JWT library.

Our JWT Decoder can help inspect a token during development. It displays token content locally, but it does not establish that the token is authentic or authorized.

Validate more than the signature

After verifying the signature, validate the claims required by your application. Common checks include:

  • iss (issuer): confirm that the expected identity provider issued the token.
  • aud (audience): confirm that the token was intended for your API or application.
  • exp (expiration): reject expired tokens.
  • nbf (not before): reject tokens that are not yet valid, when this claim is used.
  • sub (subject): interpret the subject only within the expected issuer and application context.

Use an explicit algorithm allowlist and follow the library's security guidance. Never accept an unsigned token merely because its header requests an algorithm such as none.

Five common JWT security mistakes

  1. Putting secrets in the payload: signed JWT payloads are readable. Do not include passwords, payment details, private keys, or sensitive medical information.
  2. Skipping verification: decoding a token is not an authorization check.
  3. Ignoring claims: validate issuer, audience, expiry, and any application-specific claims.
  4. Using weak or exposed signing keys: generate keys securely, store them in a protected server-side secret store, and plan rotation.
  5. Choosing unsafe browser storage: consider the XSS and CSRF trade-offs of cookies and web storage. Use Secure, HttpOnly, and appropriate SameSite cookie settings when cookies are part of the design, and implement CSRF protection where required.

Token lifetime and revocation

Keep access tokens no longer-lived than necessary. A short expiry limits the window in which a stolen token can be used, but applications also need a plan for refresh, revocation, key rotation, and logout. The right design depends on the threat model and identity provider.

Inspect tokens carefully

For development and debugging, our JWT Decoder displays the header and payload in your browser. Local processing reduces exposure to a third-party decoder, but it does not make a live production token safe to share. Use synthetic or test credentials whenever possible.

Summary

JWT security depends on verification and validation, not on hiding the payload. Verify signatures on the server, restrict accepted algorithms, validate claims, protect signing keys, and design token storage and lifetimes around your application's risks.

سوالات متداول

آیا رمزگشایی JWT به معنای هک کردن آن است؟

خیر. JWT ذاتاً کدگذاری شده است (Base64URL) و هر کسی می‌تواند محتوای آن را بخواند. "رمزگشایی" فقط خواندن اطلاعات است. امنیت JWT به امضای دیجیتال (Signature) بستگی دارد، نه به مخفی بودن محتوا.

آیا می‌توان از JWT برای ذخیره اطلاعات حساس استفاده کرد؟

هرگز. هرگز داده‌های حساس مثل رمز عبور، شماره کارت بانکی یا اطلاعات پزشکی را در Payload ذخیره نکنید. JWT فقط برای انتقال اطلاعات شناسایی (Identity) مثل User ID یا نقش‌ها مناسب است.

چگونه JWT را در سرور امن نگه داریم؟

امضای JWT باید در سرور با استفاده از کتابخانه‌های معتبر (مثل jsonwebtoken در Node.js) بررسی شود. هرگز امضا را در سمت کلاینت (مرورگر) تایید نکنید، چون کلید مخفی (Secret) در دسترس خواهد بود.

آیا می‌توانم از ابزار JWT Decoder شما برای توکن‌های واقعی استفاده کنم؟

بله، چون پردازش ۱۰۰٪ محلی است و توکن به هیچ سروری ارسال نمی‌شود. اما برای امنیت بیشتر، توکن‌های حیاتی تولید را در محیط توسعه تست کنید، نه در نسخه Production.

Frequently Asked Questions

Does decoding a JWT mean it has been hacked?

No. A typical signed JWT uses Base64URL encoding for its header and payload, so those parts can be read. Decoding does not reveal or break the signing key and does not verify authenticity.

Can I put sensitive information in a JWT payload?

Do not put secrets or sensitive personal data in an ordinary signed JWT. Its payload is readable by anyone who obtains the token unless a separate encryption standard is used.

Where should a JWT signature be verified?

Verify the signature on the trusted server or resource that makes the authorization decision. Use a maintained library and an explicit algorithm allowlist, and validate relevant claims.

Is a browser JWT decoder safe for production tokens?

Local decoding can avoid sending a token to a remote service, but production tokens are still credentials. Prefer test tokens and never paste a live bearer token into a tool unless your security policy explicitly permits it.
