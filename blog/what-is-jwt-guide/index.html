JWT چیست؟ راهنمای جامع توکن‌های وب (مبتدی تا پیشرفته)

📅 ۲۰ آذر ۱۴۰۵ ⏱️ ۷ دقیقه مطالعه

اگر به دنبال پیاده‌سازی امن و جلوگیری از آسیب‌پذیری‌های JWT هستید، مقاله راهنمای امنیت JWT ما را بخوانید.

در دنیای برنامه‌نویسی وب مدرن، JWT (JSON Web Token) یکی از پرکاربردترین مفاهیم برای احراز هویت (Authentication) است. اگر با APIها، اپلیکیشن‌های موبایل یا میکروسرویس‌ها کار کرده باشید، حتماً نام آن را شنیده‌اید. اما JWT دقیقاً چیست و چرا این‌قدر محبوب شده است؟

JWT چیست؟

JWT یک استاندارد باز (RFC 7519) برای انتقال امن اطلاعات بین دو طرف (کلاینت و سرور) به صورت یک شیء JSON است. این اطلاعات به صورت دیجیتال امضا می‌شوند تا از جعل و دستکاری محافظت شوند.

ساختار JWT

یک توکن JWT از سه بخش تشکیل شده که با نقطه (`.`) از هم جدا می‌شوند:

  1. Header (سرآیند): شامل نوع توکن (JWT) و الگوریتم امضا (مثل HS256).
  2. Payload (داده‌ها): شامل اطلاعات کاربر (مثل User ID، نقش‌ها) و زمان انقضا (exp).
  3. Signature (امضا): برای تایید اصالت توکن. این بخش با کلید مخفی سرور تولید می‌شود.

چرا JWT محبوب است؟

  • Stateless: سرور نیازی به ذخیره Session ندارد و درخواست‌ها را با خود توکن بررسی می‌کند.
  • مقیاس‌پذیر: برای سیستم‌های توزیع‌شده و میکروسرویس‌ها عالی است.
  • چند سکویی: در وب، موبایل و حتی IoT کار می‌کند.

JWT vs Session

در روش سنتی Session، سرور یک شناسه (Session ID) تولید می‌کند و اطلاعات کاربر را در حافظه خود نگه می‌دارد. اما در JWT، تمام اطلاعات در خود توکن قرار دارد و سرور فقط امضا را بررسی می‌کند. این تفاوت باعث می‌شود JWT برای سیستم‌های بزرگ و توزیع‌شده مناسب‌تر باشد.

نکات امنیتی مهم

  1. هرگز اطلاعات حساس در Payload ذخیره نکنید: رمز عبور، شماره کارت و... هرگز نباید در JWT باشند. چون Payload فقط Base64 است و قابل خواندن است.
  2. تاریخ انقضا (exp) را حتماً تنظیم کنید: توکن‌های بدون انقضا خطرناک هستند.
  3. امضا را در سرور بررسی کنید: هرگز به امضای سمت کلاینت اعتماد نکنید.

جمع‌بندی

JWT یک ابزار قدرتمند برای احراز هویت است، اما استفاده از آن نیاز به دانش امنیتی دارد. اگر به درستی پیاده‌سازی شود، می‌تواند تجربه کاربری و مقیاس‌پذیری سیستم شما را به شدت بهبود بخشد.

JSON Web Token (JWT) is a compact format for representing claims that can be transferred between parties. It is commonly used in authentication and API authorization, but it is important to understand what a token proves—and what it does not prove.

What is a JWT?

JWT is defined by RFC 7519. A JWT can carry claims about a subject and the context in which the token should be used. A signed JWT allows a receiving system to detect changes to the token when it verifies the signature with a trusted key.

The three parts of a compact signed JWT

A common signed JWT has three segments separated by periods:

  1. Header: describes the token type and the algorithm used to create the signature.
  2. Payload: contains claims such as subject, issuer, audience, and expiration time.
  3. Signature: provides integrity and issuer authenticity when correctly verified.

The header and payload are typically Base64URL-encoded. Encoding is not encryption, so do not place secrets or sensitive personal information in a readable token payload.

Why applications use JWTs

  • Interoperability: JWT is a documented format supported by many programming languages and libraries.
  • Compactness: a token can be transmitted in an HTTP header or another agreed transport.
  • Distributed systems: services can validate tokens using trusted keys without looking up a session record for every request, if the architecture is designed for that model.

These benefits do not mean JWT is always the best choice. Key management, revocation, token size, and the need for immediate permission changes all affect the design.

JWT compared with server-side sessions

With a traditional session, the server stores session state and the browser usually holds an opaque session identifier in a cookie. With a JWT-based design, the client sends a token containing claims that a service verifies. Sessions make centralized invalidation straightforward; self-contained tokens can simplify distributed validation but require careful expiry, revocation, and key-rotation planning. Choose based on your application's threat model and operational needs.

Essential security practices

  1. Never treat decoding as proof of authenticity; verify the signature.
  2. Validate issuer, audience, expiry, and other claims required by your application.
  3. Use a strict algorithm allowlist and a maintained JWT library.
  4. Keep signing keys secret, high-entropy, and protected on trusted servers.
  5. Keep tokens short-lived and design refresh and revocation deliberately.
  6. Do not store passwords or other secrets in a readable payload.

Summary

JWT is a standardized way to carry claims between systems. It can support distributed authentication architectures, but safe use requires signature verification, claim validation, key protection, and a deliberate token lifecycle. For a deeper security checklist, read our JWT security guide.

سوالات متداول

JWT یک روش رمزنگاری است؟

خیر. JWT فقط یک استاندارد برای تولید توکن است. محتوای آن Base64 است و هر کسی می‌تواند آن را رمزگشایی کند. امنیت JWT به امضای دیجیتال (Signature) آن بستگی دارد، نه به مخفی بودن محتوا.

تفاوت JWT و Session چیست؟

Session در سرور ذخیره می‌شود اما JWT در سمت کلاینت (مرورگر) ذخیره می‌شود. JWT برای معماری‌های میکروسرویس و APIها مناسب‌تر است، اما Session برای برنامه‌های سنتی امنیت بیشتری دارد.

چرا JWT محبوب است؟

چون Stateless است. یعنی سرور نیازی به نگهداری اطلاعات نشست (Session) ندارد و می‌تواند به راحتی مقیاس‌پذیر باشد. همچنین برای احراز هویت در اپلیکیشن‌های موبایل و APIها عالی است.

آیا JWT امن است؟

اگر به درستی پیاده‌سازی شود، بله. اما اشتباهات رایج مثل ذخیره اطلاعات حساس در Payload یا عدم بررسی تاریخ انقضا (exp) می‌تواند خطرناک باشد. همیشه امضا را در سرور با کلید مخفی بررسی کنید.

Frequently Asked Questions

Is a JWT encrypted?

A typical signed JWT is encoded, not encrypted. Its header and payload can be read by anyone who has the token. JWT also supports encrypted forms, but signed tokens alone do not provide confidentiality.

What is the difference between a JWT and a session?

A session commonly uses a server-side record referenced by a cookie. A JWT carries claims in a token. Both approaches have security and operational trade-offs; neither is automatically more secure.

Why are JWTs used?

JWTs provide a compact, standardized way to carry claims between systems. They are commonly used in APIs and distributed applications when their validation and lifecycle are designed carefully.

Is a JWT safe to use?

It can be used safely when signatures and claims are validated, keys are protected, tokens have appropriate lifetimes, and sensitive information is not exposed in readable payloads.
